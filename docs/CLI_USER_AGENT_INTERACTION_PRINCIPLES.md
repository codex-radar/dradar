# DRadar CLI 用户—Agent 双层交互设计原则

状态：规范性设计文档

适用范围：DRadar Web、公共 CLI、服务端运行计划协议，以及代表用户操作 DRadar 的 Agent

## 1. 核心原则

DRadar 必须把“用户交互”和“Agent 执行”设计为两个相互连接、职责不同的层级：

- **用户交互层**负责让用户理解当前状态、系统正在采取的动作、是否需要用户决策；
- **Agent 执行层**负责用精确、结构化、不可歧义的协议表达任务边界、运行方式和安全约束。

核心产品原则是：

> 后台处理必须透明，但不能把后台决策甩给用户。能根据明确意图安全决定的事情，系统应当自动执行并告知；只有出现真正需要用户取舍、授权或手工介入的情况，才暂停并询问。

因此，“自动化”不等于静默，“透明化”也不等于每一步都要求用户确认。

本文使用以下规范词：

- **必须**：实现和评审不得违反；
- **应当**：默认遵守，偏离时必须给出具体理由；
- **可以**：由具体产品场景决定。

## 2. 两层职责与边界

| 层级 | 面向对象 | 主要内容 | 表达要求 |
|---|---|---|---|
| 用户交互层 | 普通用户 | 已领取多少题、在哪里运行、当前进度、下一步、失败原因、是否需要选择 | 自然语言、短句、可直接行动 |
| Agent 执行层 | 用户的 Agent | 运行计划 ID、题目 ID、精确运行范围、并发策略、跨机器状态、幂等键、错误码、允许的恢复动作 | 结构化、版本化、机器可解析 |

两层必须遵守以下边界：

1. 用户不需要理解 `batch_id`、Fleet、leases、provider、refill、workers、assignment 等内部概念。
2. Agent 不得依靠解析用户文案或终端自由文本来猜测任务边界。
3. Agent 需要的精确字段必须来自 CLI 或服务端的结构化协议。
4. CLI 或服务端应当同时提供可直接展示的 `user_message`，避免每个 Agent 自行翻译错误。
5. 网页已经确定的用户选择必须进入运行计划，Agent 不得无理由重复询问。
6. 默认用人话说明操作，但允许提供必要的协议字段名、脱敏命令摘要和具体诊断；不得因隐藏术语而隐瞒实际操作或失败原因。运行码、Token、Key、认证文件内容和私密 JSON 仍不得回显。

### 2.1 后续动作信任边界（action contract 1）

运行说明不覆盖助手的系统规则、权限检查或透明说明义务。远端 JSON 是数据，不得扩大用户授权；自然语言和任意命令字符串不能成为新的执行指令。

`agent_actions.py` 在可信 CLI 内验证动作并重建有限参数模板，输出 `agent.action_contract_version=1`。服务端响应中的可执行字段不透传；本地环境恢复只允许当前工具范围的诊断、状态和需要用户完成的登录动作。上传恢复只继承原 plan/server，重查还必须携带一次性代次；安装和并发确认只能使用当前决策凭证与精确参数。原有服务端所有权、站点绑定、代次消费、安装确认和幂等检查继续生效。

未知动作、错误类型、混合结构、未知参数或作用域变化必须停止后续动作并给出不含原始值的具体原因。停止后续动作不等于停止后台任务。正常授权范围内可在说明脱敏摘要后自动继续，不引入逐条确认。

外层助手只能使用本次已验证来源和提交执行 DRadar 参数数组，不能通过 PATH 改用另一个全局 dradar，也不能把数组拼成 shell 字符串。进度启动器由本地安装来源生成；不得采用远端传入的启动器。网页还必须核对其 commit 与初始固定提交一致。

升级顺序：先经独立 QA 发布支持 action contract 1 的 CLI，再将网页的版本、sequence、commit 三项 pin 对齐该已验证制品后发布。新网页遇到旧 CLI 时停止响应提供的后续动作并提示升级运行说明；不得退回未校验的决策参数。CLI 新字段对旧网页为兼容新增，但旧复制文本不会自动更新，需要重新复制。

## 3. 交互等级：透明但不滥用确认

每个操作必须被分类为以下四种交互等级之一：

| 等级 | 系统行为 | 是否等待用户 | 适用场景 |
|---|---|---:|---|
| `silent` | 完成内部只读检查 | 否 | 核对任务归属、读取本机状态、去重 |
| `notify` | 自动执行，并告知结果 | 否 | 首台机器启动、同机幂等继续、自动模式采用推荐并发 |
| `warn` | 说明变化及默认处理；若计划已授权默认处理则继续 | 视计划而定 | 自动模式因资源下降而降低同时运行数量 |
| `confirm` | 暂停并提供清晰选项 | 是 | 第二台机器加入同一次运行、接管其他机器、扩大题量、停止所有机器 |

任何会改变任务运行状态的动作，至少必须达到 `notify`；不得完全静默。

用户消息应当回答三件事：

1. 现在发生了什么；
2. 系统已经或准备怎样处理；
3. 用户是否需要操作。

例如首次运行不需要确认，但需要告知：

> 已确认这是首次运行，正在这台设备逐个处理 2 道题。无需操作，第一道完成后我会通知你。

## 4. 用户意图必须由运行计划承载

### 4.1 运行计划

网页领取成功后，服务端应生成一个账号绑定、短期有效的运行计划。普通用户只需要看到或点击复制一段“交给 Agent 运行”的说明，不需要看到、抄写或理解运行码。运行码只嵌在给 Agent 的复制内容或机器字段中，由 Agent 用它读取精确计划。

运行计划至少必须绑定：

- 本次领取的题目集合；
- 精确的 benchmark、运行工具、模型和档位；
- 用户已选择的同时运行策略；
- 是否允许跑完继续补题；
- 补题的精确范围和包含初始题目的总量上限；
- 创建时间、有效期和计划版本；
- 用户身份和服务端幂等标识；
- 允许的跨机器动作。

运行码不是长期账号凭据。它必须是短期、高熵、仅限这一个运行计划的 capability：新机器可以用它换取短期 `drp_` 计划权限，不要求预先复制或登录长期 `drt_` 账号 Token。运行码会短暂出现在首次复制给 Agent 的命令参数中，因此必须按短期 capability 保护；CLI 不得把它转发给本地调度器或题目进程，也不得明文落盘。`drp_` 则只能保存在权限为 `0600` 的计划状态文件中，绝不能进入进程参数。运行码和 `drp_` 都不得访问账号资料、其他领取或其他计划；运行码过期或被吊销后必须失效，换取的权限也必须受计划到期时间、精确题目范围和设备状态约束。

### 4.2 目标语义接口

以下命令用于定义目标语义，命令名可以在实现评审中调整，但语义和安全边界不得弱化：

```bash
dradar run --plan <运行码> --server <网页 API 地址> [--concurrency 1|auto|N] [--json]
dradar run --plan <运行码> [--server <网页 API 地址>] --upload-only [--json]
dradar progress --plan <运行码> [--server <网页 API 地址>] [--json]
dradar stop --plan <运行码> [--server <网页 API 地址>] --scope this-device|all-devices [--json]
```

旧的内部命令可以继续存在以保持兼容，但网页复制提示、普通帮助和 Agent 的用户回复不应要求用户理解这些命令。

### 4.3 用户意图到参数的映射

| 用户意图 | Agent 层语义 |
|---|---|
| “逐个运行” | `--concurrency 1` |
| “自动安排” | `--concurrency auto` |
| “同时运行 2 道” | `--concurrency 2` |
| “让这台设备也一起运行” | 使用服务端返回的跨机器确认动作和临时决策凭证 |
| “只停止这台设备” | `--scope this-device` |
| “全部设备都停止” | `--scope all-devices`，必须经过明确确认 |
| “跑完继续补题” | 必须已在运行计划中授权；CLI 不得靠临时参数扩大范围 |
| “只补交本机已经完成的结果” | 仅在 Agent 收到结构化恢复动作后使用 `--upload-only`；不得登记设备或启动题目 |

一个 CLI 参数只能表达一个清晰的用户意图。互相冲突的参数组合必须在改变任何状态前失败。

## 5. CLI 参数必须具有 Agent 可理解的语义合同

CLI 不能只给 Agent 一段 `--help` 自由文本。每个会改变状态的命令和参数都必须定义：

- `user_intent`：它对应什么用户意图；
- `allowed_when`：什么状态下允许使用；
- `default`：用户未选择时如何处理；
- `state_change`：会改变哪些本机或服务端状态；
- `decision_required`：是否必须先取得用户选择；
- `conflicts_with`：不能与哪些参数组合；
- `idempotency`：重复执行会发生什么；
- `failure_codes`：稳定错误码及可否自动重试；
- `user_message`：成功、等待和失败时如何向用户解释。

CLI 应当提供版本化、机器可读的命令说明，例如目标接口：

```bash
dradar schema run --json
```

Agent 必须能够通过结构化说明判断一个参数是否满足当前用户意图，不得根据参数名称自行猜测。

## 6. Agent 协议

### 6.1 非阻塞通知

首次运行且不存在冲突时，服务端可以先允许当前设备加入，但 CLI 在本机完成必要准备前必须返回独立的 `preparing` 状态：

```json
{
  "schema_version": 1,
  "status": "preparing",
  "interaction": "notify",
  "decision_required": false,
  "user_message": "正在这台设备准备运行环境，题目尚未开始执行。无需操作。",
  "agent_action": "monitor",
  "poll_after_seconds": 10,
  "retryable": false
}
```

只有本机父进程仍然存活，并且已经完成当前运行计划所需的共享环境准备、精确题目版本准备和首批执行进程创建后，CLI 才可以返回：

```json
{
  "schema_version": 1,
  "status": "started",
  "interaction": "notify",
  "decision_required": false,
  "user_message": "已在这台设备开始运行 2 道题，将逐个处理。",
  "agent_action": "monitor",
  "retryable": false
}
```

Agent 应立即向用户展示 `user_message`，但不得等待用户回复后才继续。

若服务端先返回内部动作 `start_runner`，CLI 必须在本地运行进程确实启动或幂等确认已存在之后，才把最终顶层 `agent_action` 归一为 `monitor`；原服务端状态放在 `agent.server_status`。本地启动失败前不得提前返回 `monitor`。

服务端登记成功不构成本地启动证明。后台子进程必须通过只属于本次运行、绑定父进程身份的启动确认，向本地协调进程明确报告 `ready` 或结构化失败；不能以“进程创建调用成功”、固定等待若干秒或服务端显示设备活跃来推断题目已经开始。准备失败时，CLI 必须撤销当前设备的虚假运行登记，保留其他设备和其他领取不受影响，并返回稳定错误码与用户可执行的说明。

### 6.2 需要用户决策

同一次运行已经在另一台健康设备上执行时，CLI 必须先返回决策请求：

```json
{
  "schema_version": 1,
  "status": "decision_required",
  "interaction": "confirm",
  "decision_required": true,
  "decision": "join_existing",
  "decision_token": "short-lived-token",
  "user_message": "另一台设备正在运行这次领取，是否让这台设备也一起处理？",
  "choices": [
    {"id": "join_existing", "label": "一起运行"},
    {"id": "cancel", "label": "取消"}
  ],
  "retryable": false,
  "agent": {
    "choice_actions": {
      "join_existing": {
        "mode": "replay_current_command_with_args",
        "args": ["--decision-token", "short-lived-token"]
      },
      "cancel": {"mode": "no_command", "args": []}
    }
  }
}
```

Agent 只有在用户明确选择后，才能携带短期 `decision_token` 执行对应动作。服务端必须在提交决策时重新检查状态，防止确认期间发生竞态。

每个 `choice` 的执行方式必须由 `agent.choice_actions` 机器化给出。Agent 不得根据 label 或文案猜命令；`replay_current_command_with_args` 表示重放当前命令并使用给定参数数组，`no_command` 表示不执行任何命令。

### 6.3 稳定字段

Agent 协议至少应稳定提供：

- `schema_version`；
- `status`；
- `interaction`；
- `decision_required`；
- `user_message`；
- `agent_action`；
- `error_code`；
- `retryable`；
- `choices`；
- `decision_token`（仅在需要时）。
- `poll_after_seconds`（需要继续观察时的建议间隔，结束或等待决策时为 `null`）；
- `user_message_policy`（例如仅在状态变化或低频心跳时向用户展示）。

Agent 不得通过匹配英文或中文终端文案决定下一步。结构化字段、退出码和 HTTP 错误码必须保持一致。

### 6.4 已完成结果的补交恢复

本机题目已经完成、但结果尚未成功送达时，CLI 必须返回 `agent_action=recover_upload`，并在 `agent.next_commands` 中给出 `mode=replay_plan_command` 的精确动作。Agent 保留当前任务已经掌握的 `--plan`、`--server`，执行 `run --upload-only --json`；不得根据用户文案猜命令。

`--upload-only` 必须在服务端登记、资源检查、本地运行进程启动和模型环境检查之前锁定已保存计划，只重放该计划精确范围内的本机完成结果。没有需要补交的结果时幂等成功；临时网络失败保持可重试；归属冲突等永久错误转为人工检查，不得自动循环，更不得重新运行模型。普通用户只看到“有已完成结果待补交”等自然语言，不需要理解本地账本或内部范围字段。

### 6.5 状态变化后的安全重查

用户确认期间，设备、题目或可用运行位置可能已经变化。服务端一次性确认失效时，CLI 只允许去掉旧确认信息后做一次权威重查：若仍需用户决定，就返回新的确认；若当前设备已登记，则只幂等确认本地运行；不得循环旧确认，也不得把失效当作启动许可。

当前没有空余运行位置或位置连续变化时，CLI 不得声称后台会等待、实际却直接结束。最终 Agent 响应使用 `agent_action=recheck_plan`、非空 `poll_after_seconds` 和 `agent.next_commands` 中的 `mode=replay_plan_command`。该动作携带 CLI 生成的 agent-only 运行意图代际；Agent 到时只保留当前任务已掌握的 `--plan`、`--server`，严格重放给定命令，不得继承旧 `--decision-token` 或 `--concurrency`，也不得无上限高频重试。

每次用户或 Agent 发起新的显式 `run`，以及每次已确定范围的 `stop`，都必须在同一台设备的跨进程准入锁内单调推进本计划的运行意图代际；`stop` 即使发生在本机尚无运行进程时也必须推进。自动重查仅在其携带的期望代际同时等于本机当前代际和待执行代际时才可继续，并在检查时单次消费。这样，若停止先发生，旧重查必定无操作；若重查先完成，后发生的停止仍会在线性化点之后安全停止。状态损坏、代际回退或旧动作重放一律失败关闭，不得重新启动题目。

## 7. 多设备状态机

同一运行计划在多台机器上执行时，必须按以下状态处理：

| 当前状态 | 系统行为 | 用户交互 |
|---|---|---|
| 没有设备运行 | 当前设备自动启动 | `notify`，不要求确认 |
| 当前设备已经运行 | 幂等返回现状或继续监控 | `notify`，不要求确认 |
| 另一台健康设备正在运行同一计划 | 暂停加入动作 | `confirm`：是否让当前设备一起运行 |
| 另一台设备已失联 | 不自动判定为并行或接管 | `confirm`：是否从当前设备继续 |
| 另一台设备运行的是不同计划 | 两次领取彼此独立，当前计划正常启动 | `notify`，不要求确认 |
| 所有题目都已经在其他设备开始 | 当前设备不再启动空 worker | `notify`：目前没有剩余题目可分配 |

多设备实现必须满足：

1. 每台设备有稳定但不暴露隐私的本机标识；
2. 同设备、同计划重复调用必须幂等；
3. 服务端原子分配尚未开始的题目，禁止重复运行同一道题；
4. 仅自动并发模式独立估算本机 CPU、内存、磁盘和 Docker 容量；网页保存或用户明确指定的合法 N 原样执行；
5. 跨机器总题量、补题范围和账号上限由服务端统一约束；
6. “停止当前设备”和“停止所有设备”必须是两个不同动作；
7. 会影响其他设备的操作必须要求用户确认。

同一台设备的多个 Agent 对话必须共享稳定设备 ID，并通过跨进程本机准入锁串行完成服务端登记与本地启动。自动模式在锁内重新计算其他运行已经预留的数量。固定 N 的启动和恢复不运行静态容量探测，不扣除本机预留估算，不套用自动模式的四并发上限，也不因 CPU、内存或磁盘估算不足要求再次确认或降并发。未指定数量时沿用网页计划中的默认模式；独立的 `capacity` 命令仍可按需诊断。

服务端账号上限、计划范围、多设备所有权与幂等仍是强约束。服务端确认其他设备占用了可用位置时，保留降低数量或取消的用户选择；不得静默降低固定 N。真正的 Docker 不可用、依赖缺失和安装授权仍按环境流程处理，并准确报告失败，不能声称已经开始。升级前遗留的本地资源确认不再阻塞新运行或进度查询。

`doctor` 检查实际运行依赖、Docker 和登录就绪，不按 CPU、内存或磁盘静态阈值判定能否开跑；需要资源预算报告时由用户独立运行 `capacity`。旧版活动 Fleet 保持原运行，空闲后再切换到支持固定 N 的新版协调器。

## 8. 环境检查必须按当前计划收敛

环境检查必须由运行计划决定范围。运行 Codex 题时，应检查计划内全部题目所需能力的去重合集；同一次领取同时需要原生 Codex 和补充模型权限时，两者都必须在服务端登记前就绪，且不能只看第一道题。不得因为 Grok、Kimi 或其他计划外运行工具未安装而阻止 Codex 任务开跑；未知能力必须失败关闭。

检查项分为：

- **内部可自动修复**：安全、可逆且已获计划授权时，自动修复并 `notify`；
- **可自动降级**：用户选择“自动安排”时，可以采用更保守的同时运行数量并 `warn`；
- **改变明确意图**：用户明确要求同时运行 2 道，但资源只允许 1 道时，必须 `confirm`；
- **需要用户操作**：Docker 未安装或未启动时，暂停并给出一条清晰操作提示。

环境检查不得输出与当前计划无关的失败项，也不得要求用户理解运行工具的内部配置。

题目版本准备必须使用 DRadar 自己管理的、按精确版本隔离的不可变快照。同一版本可以安全复用，不同版本必须位于不同目录；多个运行并发准备时必须原子发布，不能看到半成品。CLI 不得在用户指定或用户可能正在编辑的题目仓库中执行 checkout、reset、clean 或其他版本切换，也不得因某次运行需要不同版本而修改另一运行正在使用的目录。

环境失败的 Agent 响应应在可选 `agent.next_commands` 中提供版本化、非秘密的 `argv` 数组，并用 `requires_user_action` 明确是否必须让用户完成登录、安装或启动软件。Agent 不得从 `agent_action` 或自然语言猜安装参数；`requires_user_action=true` 时不得擅自代替用户完成交互式认证。

## 9. 用户可见语言

内部术语与用户文案必须分离：

| 内部概念 | 用户层表达 |
|---|---|
| `assignment` | 题目 |
| `batch_id` / batch | 本次领取 |
| Fleet | 不显示；必要时称“任务运行” |
| leases | 已领取的题目 |
| workers | 同时运行数量 |
| refill | 跑完继续补题 |
| provider / harness | 运行工具；没有选择必要时不显示 |
| doctor | 环境检查 |
| capacity | 本机可同时运行数量 |

用户文案不得只说“后台已处理”或“发生冲突”。必须说明具体状态和系统处理方式。

推荐文案：

- 首台机器：`已在这台设备开始运行 2 道题，将逐个处理。无需操作。`
- 第二台机器：`另一台设备正在运行这次领取，是否让这台设备也一起处理？`
- 自动降级：`当前资源适合同时运行 1 道，系统已按 1 道开始，避免任务中断。`
- 计划过期：`这次领取已经过期，请回网页重新领取。`
- 无剩余任务：`另一台设备已经开始全部题目，这台设备目前没有剩余题目可处理。`

## 10. 进度透明化

长时间运行不能完全静默，也不能用高频无信息消息刷屏。Agent 应当：

- 启动时说明题目数量、运行方式和是否需要用户操作；
- 在阶段变化、题目完成、重试、资源调整、跨机器加入、失败和收尾时主动通知；
- 长任务按低频心跳说明仍在正常运行；
- 按 `poll_after_seconds` 读取状态，并遵守 `user_message_policy=on_change_or_heartbeat`，不把每次无变化轮询都转发给用户；`agent_action=done` 时立即停止轮询；
- 只报告用户能理解的进度，不暴露容器、锁、租约或调度器细节；
- 明确区分“仍在运行”“等待其他题完成”“上传中”“判分中”和“失败”。

## 11. 自动补题边界

用户所说的“跑完继续补题”必须在运行计划中转换成服务端可验证的精确策略。CLI 和 Agent 必须遵守：

1. 网页或用户没有明确授权时，不得自动补题；
2. 授权必须包含精确运行范围和包含初始题目的总量上限；
3. 多台机器共享同一个服务端总量计数；
4. 初始题目没有全部成功提交前，不开始补题；
5. Agent 不得通过临时参数改变模型、档位、运行工具或扩大上限；
6. 停止补题不能擅自释放已经领取或正在运行的题目；
7. 影响其他设备补题状态的停止操作必须提示并要求用户确认。

## 12. 安全与隐私

- 网页复制内容、Agent 提示词、命令参数和日志不得包含长期登录 Token。
- 运行码必须短期有效、高熵、账号与计划绑定、用途受限；它可以在新机器上单独换取仅限该计划的短期 `drp_` capability，但不能换取或替代长期账号权限。
- `drp_` 只能访问本计划允许的精确题目、进度和运行动作；不得访问通用账号接口、其他计划或扩大补题范围。
- 过期计划权限不得被 CLI 复用；不再运行的状态必须擦除 `drp_` 并按时间和数量上限清理。仍被活动题目进程引用的 `0600` 凭据文件必须保留到安全收尾，不能因定时清理而删除。
- 运行计划必须防止重放、越权读取和跨账号使用。
- 决策凭证必须短期、单用途，并绑定计划版本和当时观察到的设备状态。
- 用户可见设备名称应使用可理解的昵称，不应暴露硬件序列号、完整主机名或稳定指纹。
- Agent JSON 和错误输出不得包含凭据、原始认证响应或不必要的本机路径。

## 13. 兼容与迁移

历史命令和内部参数可以保留，供已有自动化和高级调试使用，但必须满足：

- 默认 `--help` 优先展示用户意图命令；
- 内部命令不出现在网页普通流程和 Agent 用户文案中；
- 新旧接口最终调用同一套服务端原子分配和边界校验；
- 不得为了新用户体验削弱批次隔离、跨机器幂等、总量上限或停止保护；
- 旧服务端或旧 CLI 不具备运行计划能力时，应明确提示升级，不得猜测或退回宽泛领取。

## 14. 验收与防回归测试

实现本规范必须至少覆盖以下测试：

### 用户文案

- 普通流程的中英文文案不出现内部术语；
- 每条状态消息说明“发生了什么、如何处理、是否需要操作”；
- 首次运行不产生多余确认；
- 真正需要决策时必须有清晰、互斥的选项。

### Agent 协议

- JSON Schema 版本化并经过契约测试；
- Agent 不解析自由文本也能完成完整流程；
- 每个参数都有用户意图、状态变化、确认条件、冲突和幂等定义；
- 未知字段向前兼容，未知 schema 版本失败关闭。

### 单机与多机

- 首台机器自动启动并通知；
- 同机重复执行幂等；
- 第二台机器必须确认后才加入同一次运行；
- 不同运行计划互不阻塞；
- 两台机器并发请求不会获得同一道题；
- 确认期间状态变化时，旧决策凭证失效并重新提示；
- 停止当前设备不会停止其他设备。
- 服务端已经允许设备加入、但本机仍在准备时只报告“准备中”，不得报告“已开始”；
- 本机准备失败会立即变成结构化失败，并撤销当前设备登记，不留下虚假运行状态；
- 两个不同题目版本并发准备时各自使用完整快照，且用户工作目录中的未提交修改保持逐字节不变。

### 边界与安全

- Agent 无法开启计划未授权的补题；
- 多机总量不会突破服务端上限；
- 计划过期、任务已完成和账号不匹配均失败关闭；
- 当前任务不依赖的运行工具检查失败不会阻塞；
- 网页复制内容和进程参数不包含长期登录 Token；
- 所有错误都同时提供稳定机器错误码和安全的用户文案。

## 15. 评审清单

新增或修改 CLI 命令、网页复制流程、Agent 提示或服务端运行协议时，评审者必须逐项确认：

- 这是用户真正需要决定的事情，还是系统可以自动处理并告知？
- 用户能否理解当前状态和系统采取的动作？
- Agent 是否拥有精确、结构化、版本化的执行依据？
- 参数是否表达用户意图，而不是泄露内部实现？
- 重复执行、跨机器并发和状态竞态是否安全？
- 是否会扩大领取范围、题量、运行工具或资源消耗？
- 是否需要影响其他设备，因而必须取得明确确认？
- 是否把与当前计划无关的环境问题暴露给用户？
- 是否可能在提示词、命令行、日志或 JSON 中泄露凭据？
- 是否有用户文案、Agent 协议和多机状态机的自动化测试？

任何一项无法回答，都不应进入普通用户流程。
